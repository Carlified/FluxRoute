hamming74 - functional result, 2026-11-03

Function: Hamming(7,4) syndrome checker.
  s1 = r1 ^ r3 ^ r5 ^ r7
  s2 = r2 ^ r3 ^ r6 ^ r7
  s3 = r4 ^ r5 ^ r6 ^ r7
  err = s1 | s2 | s3
Clocked pads: 7 inputs (r1..r7), 4 outputs (s1__spl_10, s2__spl_12, s3__spl_8, err).
Target: 4 pipeline levels at 8 GHz
(period 125 ps); input window 68.2..170.5 ps,
chosen centre phase 119.35 ps.

The outputs keep the splitter-branch names of the nets that drive the pads
(s1__spl_10 etc.); they carry the syndrome bits s1, s2, s3 and err.

--- from .cir to a viewable, verified waveform ---

Run from the repository root; the design folder holds hamming74.cir,
hamming74.tb.json and hamming74.vectors.json.

  $design = "Win64/Release/output/hamming74"    # examples/outputs/hamming74 on a checkout

1. Read the exported metadata:
     Get-Content $design/hamming74.tb.json
   inputs r1..r7   outputs s1__spl_10, s2__spl_12, s3__spl_8, err
   frequency, pipeline levels, input window and output travel are in this file.

2. Build the stimulus for all 128 patterns and the expected outputs; the
   vectors are in hamming74.vectors.json and spelled out at the end of this
   file.  Pattern k assigns r1..r7 to bits 6..0 of k.

3. The 128 patterns do not fit one run.  A single 0.2 ps deck needs 82830
   time points (make_tb refuses anything over 80000) and a single 0.25 ps run
   (66264 points) crashes JoSIM with 0xC0000409 on this 2119-line,
   296-junction netlist.  Split the vectors into four 32-pattern decks; the
   decode grid is the same for every chunk because each chunk's first pattern
   launches at the same phase:
     python tools/make_tb.py --dir $design `
       --bits "r1=<bits 0-31>,...,r7=<bits 0-31>" --slots 32 `
       --out $design/hamming74_tb_a.cir --run --decode --expect "<expected 0-31>"
   repeat with the next 32-character slices into _tb_b, _tb_c and _tb_d.
   Each chunk is 22830 points (4566 ps at 0.2 ps) and completes in ~15 s.

4. The decode window starts at watch + 1 period (make_tb default):
     clock send  50 ps     data launch 169.35 ps
     watch       466 ps  = clock send + 4 periods + travel
     decode      591 ps  = watch + 1 period (auto: first capture edge after the data)
     period 125 ps   slots 32 per chunk   step 0.2 ps

5. Build the I/O-port deck for each chunk and look for one pulse per bit on
   every pad:
     python tools/make_tb.py --dir $design `
       --bits "r1=<bits>..." --slots 32 --io-nodes `
       --out $design/hamming74_io_tb_a.cir --run
   (again for _b, _c, _d)

6. View the waveforms (chunk a shown; any chunk works the same way):
     python tools/josim-plot.py $design/hamming74_io_tb_a.csv -t stacked `
       -x $design/hamming74_io_trace_a.html
   (open hamming74_io_trace_a.html: clock, r1..r7 as inputs, s1/s2/s3/err as outputs)

--- result ---

All 128 input combinations, decoded twice on the same shared grid:
  phase traces   P(B1|XR<out>): OK on all four chunks
  pad pulses     V(<out>_o): 128/128 bits per output, matches the expectation
  input pads     V(<in>_i): all 896 stimulus bits read back exactly
The die is functionally correct at 8 GHz with the chosen centre phase.
A single-bit error is named by the syndrome and flagged by err, so the
checker behaves as a Hamming(7,4) decoder front end.

Files:
  hamming74_tb_a..d.cir/.csv/.meta.json     phase probes, 32 patterns each
  hamming74_io_tb_a..d.cir/.csv/.meta.json  I/O port probes, 32 patterns each
  hamming74_io_trace_a.html                 stacked I/O trace (regenerated by step 6)
  hamming74.vectors.json                    stimulus and expected outputs, all 128
